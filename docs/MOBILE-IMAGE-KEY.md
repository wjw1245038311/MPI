# 手机端图片：快照只发元数据，字节按需拉取

> **状态：设计稿（未实现）** ｜ 2026-11-06
> 触发问题：会话里图片一多，手机端只看到最早 1–3 张，其余图**整块消失且点不开**；
> ComfyUI 批量出图的场景直接撞死。
>
> 相关文档：`docs/attachment-content-addressing.md`（内容寻址对象库）、
> `docs/MOBILE-NATIVE-DESIGN.md`（断线恢复契约）、`src/main/remote/history-limit.ts`（字节预算）。

---

## 1. 现状与问题（代码事实）

| 项 | 现状 | 出处 |
| --- | --- | --- |
| 快照图片总预算 | **240 KB**（base64 字符） | `src/main/ipc.ts` `imageBudget = 240_000` |
| 单张缩略图 | 1280 宽 JPEG q78，base64 常见 60–150 KB，硬顶 160 KB | `src/main/attach-file-thumbs.ts`、`chat-attachment-store.ts storeThumbnail` |
| 因此一次能带 | **1～3 张** | 推算 |
| 图片窗口 | 只下发**最近 12 条消息**里的图 | `ipc.ts` `IMAGE_RECENT_MESSAGES` |
| 预算消耗方向 | **从旧到新**——窗口内最旧的先吃预算，**最新的图先被砍** | `ipc.ts`（`source.forEach` 升序） |
| 超预算 / 超窗口 | `return null`，**整个块不下发** | `ipc.ts` 两处 `return null` |
| 客户端拿不到块 | 什么都不显示（「图片无法显示」只在块存在时才出） | `ThreadScreen.kt` `ImageBlock` |

**结论**：不是"变慢"，是**静默丢内容且无占位、无 key、点不开**。与 2026-11-06 修的「每回合最多 80 块」
（`.slice(0, 80)` 砍掉回合末尾正文）属于同一类缺陷。

**对照组**：`file` / `video` / `audio` 块**早就是**「只发元数据 + `omitted:true`，点开按需拉」。
只有 `image` 还在内联 base64。本设计不是发明新机制，是**把 image 对齐到已有口径**。

---

## 2. 目标 / 非目标

### 目标

1. 快照体积与图片**数量**解耦：30 张图 ≈ 30 KB 元数据，而不是 240 KB 只装 3 张。
2. 图片不再因为预算被**静默丢弃**：任何情况下块都在、`key` 都在、都能点开。
3. 气泡里**能看清**（含截图文字），点开能看原图。
4. 存量老会话（只有内联 base64、没落库）自动迁移，不要求用户重发。
5. 旧客户端不炸（能力协商 + 双分支并存）。

### 非目标（本期不做）

- 视频/音频/文件链路的改造（已经是元数据 + 按需拉，无需动）。
- 云端暂存媒体字节（中继只转发，见 §12 取舍）。
- 图片编辑、多选批量下载。

## 3. 交互契约：三级，各司其职

```
快照里每张图（≈1 KB 元数据）
  key      = sha256 内容地址（稳定身份，不是 URL）
  lqip     = 极低分辨率模糊占位，几百字节 → 只为「不闪白 + 不跳布局」
  thumb    = "<key>.thumb.<ext>"（主机已生成时可给名字）
  w/h/bytes= 尺寸与大小 → 先撑好布局，再加载
        │
        │ 滚到可见（±1 屏预取，并发 ≤4）
        ▼
  缩略图（气泡里显示）  ── 目标：看清大意 / 截图文字（见 §4）
        │
        │ 点开
        ▼
  原图（查看器）        ── 逐字核对、保存、分享
```

**三级的分工必须写清，避免把可读性寄托在 LQIP 上**：

| 级 | 体积 | 能做什么 | 不能做什么 |
| --- | --- | --- | --- |
| LQIP | 0.3–1 KB（长边 ≤40px） | 占位色块、消除布局跳动、断网时也有个形 | **读不了任何字**（20×15 像素没有字的几何信息） |
| 缩略图 | 60–600 KB（按内容类型） | 气泡里辨认内容；截图档**能读字** | 逐字校对小字、看细节 |
| 原图 | 原始大小 | 一切 | 流量大（只在点开时拉一次） |

> LQIP 放大像素数没有意义：可读性是**分辨率 × 压缩质量**的函数，靠 `thumb` 档解决。
> 参考 Telegram TDLib 的 `minithumbnail`：长宽「usually doesn't exceed 40」、JPEG —— 业界把「内联占位」
> 就定位在这个量级，没人指望它可读。

### 3.1 关于「截图要能读字」

**两条互不相干的路径，别混在一起**：

| 谁要读字 | 走哪份字节 | 受本设计影响吗 |
| --- | --- | --- |
| **用户**在手机上读 | 缩略图（气泡）/ 原图（点开） | 是 → 靠 §4 的截图档 |
| **agent / 模型**识别 | **原图 base64**（pi 的图片输入必须是 base64） | 否 → 完全不受影响 |

也就是说：模型识别文本从来走原图，本设计不动它；用户可读性靠「按内容类型分档的缩略图 + 点开原图」。

## 4. 缩略图分档策略（回应可读性）

现有 `ensureAttachImageThumb` 只按「1280 宽 / JPEG q78」一档生成，且 `storeThumbnail` 有 **160 KB 硬上限**
（原本是给视频封面定的）。截图类内容在这种参数下：细笔画文字会出现振铃、边缘发糊，读小字很吃力。

### 4.1 分两档生成

| 档 | 判定 | 参数 | 典型体积 | 业界对照（见 §4.5） |
| --- | --- | --- | --- | --- |
| `photo` | 默认（JPEG 源、色彩丰富） | 1280 宽，JPEG q78 | 60–150 KB | 微信约 1280 长边 / q≈0.5；WhatsApp 标准质量实测 1280–1600 长边 |
| `text` | 截图类（见 4.2） | **1600 宽，PNG 量化（≤256 色）或 JPEG q92**，上限放宽到 **600 KB** | 150–500 KB | WhatsApp 上限已到 1600；截图要保笔画，所以质量档取到 q92/无损 |

为什么截图要用 PNG：JPEG 的 DCT 量化在**高频细节（文字边缘）**上产生振铃，q78 下 12px 中文会糊成一团；
PNG 无损（量化到调色板）能保住笔画。代价是体积，但**按需拉取后单张体积只影响下载流量，不再影响快照**。

### 4.2 截图判定（启发式，可调，全部标注为经验规则）

优先按可靠度排序，命中即归 `text` 档：

1. 源 MIME 是 `image/png` 或 `image/webp`（照片极少走 PNG）；
2. 量化后颜色数 ≤ 256（UI 截图的典型特征）；
3. 宽高比落在常见屏幕比例（16:9 / 16:10 / 9:19.5 / 4:3）±2%；
4. 像素密度异常高但色彩少（Retina 截图）。

> ⚠️ 上述四条是**工程启发式，没有权威依据**，实现时写成可配置常量 + diag 日志记录判定结果，
> 便于真机回看「某张图为什么走了 photo 档」。宁可判错成 `text`（大一点但清楚），不要判错成 `photo`。

### 4.3 生成时机：后台预生成，快照只读盘

快照函数是同步的（`readThumbnailBase64` 同步读盘）。ComfyUI 一次 30 张图，**不能在快照里现场解码+缩放**
（主进程会卡 1–2 秒，手机端表现为"打开会话转圈"）。做法：

- 附件入库时（用户发图 / `storeObject` / `mpi_attach_file`）**排队**生成 `thumb` 与 `lqip`，落盘：
  - `<key>.thumb.<ext>`
  - `<key>.lqip.jpg`（20×15，约 0.3–1 KB）
- 快照**只读盘**：有就带上 `thumb` 名字与 `lqip`，没有就只带 `key`（客户端显示灰块，下次快照补）。
- 存量老图：首次进快照时投递到同一个后台队列（懒回填），不阻塞当前快照。

### 4.4 客户端选档

v1 只做两档：`thumb`（气泡）与 `original`（点开）。高 DPR 手机上 1600 宽的 `text` 档在约 360dp 宽气泡里
相当于 4.4× 像素比，足够读字。**后续可选**：按屏幕密度请求 1x/2x 档，省流量。

## 4.5 业界参考（为什么是这些数字，而不是试错）

### 4.5.1 官方文档（可引用）

| 产品 | 事实 | 来源 |
| --- | --- | --- |
| **Slack** | 一个文件同时生成**多档**缩略图：`thumb_64`（64×64）、`thumb_80`（固定 80×80，源图更小则透明填充）、`thumb_160`、`thumb_360`（最长边 ≤360，可变），以及 `thumb_480/720/800/960/1024`（视源文件大小出现）；另有 `thumb_tiny` —— **base64 内联小缩略图** | docs.slack.dev「File object」 |
| **Telegram** | `minithumbnail`：长宽「usually doesn't exceed 40」、JPEG，专门当**内联占位**；`PhotoSize` 是**多档**（每档带 width/height/file_size）；上传方给文档配的 `thumb` 要求 **JPEG、<200 kB、宽高 ≤320** | Telegram TDLib / Bot API 文档 |
| **Discord** | CDN 支持 `?size=`，**16–4096 之间任意 2 的幂** —— 客户端按需请求尺寸，服务端按需生成 | Discord 开发者文档 |
| **飞书** | 官方**没有公开**气泡缩略图尺寸；只公开上传约束：图片 ≤10 MB、GIF ≤2000×2000、其他 ≤12000×12000、返回 `image_key`；消息卡片建议尺寸 1500×3000 内 | 飞书开放平台「上传图片」「图片组件」 |

### 4.5.2 逆向与实测（可信度中等，参数会随版本漂移）

| 产品 | 事实 | 来源性质 |
| --- | --- | --- |
| **WhatsApp** | WhatsApp Web 常量：`IMG_THUMB_MAX_EDGE: 100`、`DOC_THUMB_MAX_EDGE: 480`、`VIDEO_THUMB_MAX_EDGE: 480`；标准质量发送实测长边 **1280–1600**、体积约为原图的 3%–17% | wppconnect-team 逆向常量 + 第三方实测 |
| **微信** | 聊天图片长边压到约 **1280**、质量 ≈**0.5**；宽高比 >2 的窄图聊天按短边 800；「原图」需手动勾选或点「查看原图」；**缩略图无论是否原图都会压缩** | 多篇逆向分析，官方无公开文档 |
| **飞书（客户端消息结构）** | 第三方逆向发现消息里带 `imageKey` + `thumbnailKey` 两个字段，服务端接受两者相同并自己渲染缩放 | 第三方插件逆向，**非官方** |

### 4.5.3 借用与不借用

| 结论 | 我们怎么做 |
| --- | --- |
| 「内联只放极低分辨率占位」是共识（Slack `thumb_tiny` / Telegram `minithumbnail` ≤40px） | LQIP 定为长边 ≤40px、≤1 KB；**不指望它可读** |
| 「气泡里显示的其实是压缩后的 1280–1600 图」，不是 100px 那档 | `photo` 档对齐 1280；`text` 档取 1600 |
| 小尺寸档（64/100/320）服务的是列表、通知、引用预览 | 我们 v1 不需要（会话列表用不到图片预览），**不做多档**；将来要列表预览再按 Slack 阶梯加 |
| 截图与照片不该共用一套压缩参数（微信 1280+q0.5 对文字不友好） | 拆出 `text` 档：PNG 量化或 q92，上限 600 KB |
| 服务端按需生成尺寸（Discord `?size=`）是最省存储的做法 | 我们**不学**：本机没有图片处理服务，且对象库要求内容寻址（同一 key 必须对应同一字节）。改为入库时预生成固定两档，落盘缓存 |
| 各家都要「点开看原图」（微信「查看原图」/ WhatsApp 文档通道） | 点开 = 原图，这条不变 |

## 5. 数据结构：image 块 v2

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `type` | `"image"` | 不变 |
| `key` | `string` | **必填**，sha256 内容地址 |
| `omitted` | `true` | 表示本体没下发（客户端据此走「可见即拉」） |
| `lqip` | `string?` | base64，≤1 KB 的模糊占位 |
| `thumb` | `string?` | `<key>.thumb.<ext>` —— 主机已生成时给，省一次探测 |
| `mimeType` | `string` | 原图 MIME |
| `width` / `height` | `number?` | 原图像素尺寸（布局占位用） |
| `bytes` | `number?` | 原图字节数（显示大小 + 进度） |
| `label` | `string?` | 可读名（截图场景常为空） |
| `data` | `string?` | **仅兼容分支**：旧客户端仍收缩略图 base64；新协议下最多放 LQIP |

体积账：30 张图元数据 ≈ 30 × 1 KB ≈ **30 KB**，占 420 KB 快照预算的 7%。

## 6. 数据流：三条来源都能落到 key

| 来源 | key 从哪来 | 缩略图/LQIP |
| --- | --- | --- |
| 用户在本机发的图 | 发送时已上传对象库（引用里的 `name` 就是 key） | 入库时生成 |
| 别的设备发的图 | 同上（内容寻址跨设备天然去重） | 同上 |
| **agent / ComfyUI 产出的内联图** | `blocksFor` 里已有的 `storeObject()` 调用，落库即得 key | **需补生成**（走同一后台队列） |
| 存量老消息（只有 base64） | 首次生成快照时 `storeObject` 懒回填 | 投递后台队列 |

> agent 递交（`mpi_attach_file`）与用户发图共用 `mediaRefToBlock`，见 `ipc.ts` 的注释。

| # | 位置 | 改什么 | 注意 |
| --- | --- | --- | --- |
| 1 | `ipc.ts blocksFor` image 分支 | 不发缩略图 base64；改为 `key + lqip + thumb + 尺寸 + omitted` | 旧客户端分支保留原行为 |

## 8. 客户端改动（PWA + 安卓同一套状态机）

```
LQIP/灰块 ──可见──► 拉 thumb ──成功──► 清晰缩略图（text 档可读字）
   │                     └──失败──► 保留占位 + 「点击重试」
   └──点开──► 本地原图（自己发的有 URI）？→ 直接用
              否则 → 拉原图（进度条）
```

| 项 | 建议 |
| --- | --- |
| 缓存 | 内存 LRU（bitmap，~32 MB）+ 磁盘 LRU（按 key 命名，跨会话天然去重，~256 MB） |
| 预取 | 可视区 ±1 屏，并发 ≤4；不预取原图 |
| 失败 / 离线 | 保留 LQIP + 可点重试；主机离线且无缓存 → 明确文案「主机离线，图片未缓存」 |
| 多图 | 一条消息里 N 张折叠成**九宫格 + 数量角标**，点开横向翻页（飞书/微信口径） |
| 旧数据 | 块没有 `key`（旧主机）→ 沿用现在的 `data` 渲染路径 |

## 9. 兼容与灰度（最容易翻车的一步）

现网客户端（安卓 0.5.172 / PWA）只认 `data`。主机突然只发 `key` → 满屏「［图片无法显示］」。

**做法：请求级能力标记（已落地，2026-11-06）**

客户端在 `thread.subscribe` / `thread.resync` / `thread.get` 的 payload 里带 `imageKeys: true`；
主机的 `getThread` options 接收它，`blocksFor` 据此决定走元数据还是老的内联分支。

> 为什么不用「设备能力注册表 + `caps`」：仓库里虽有 `E2E_BINARY_CAP` 的先例，但那是**握手期**的
> 一次性能力；图片这个需求只需要「本次请求要不要新格式」。请求级标记天然无状态：客户回滚旧版本、
> 换浏览器、清缓存、多设备混用都自动生效，主机不需要维护任何设备能力表，也不需要发版顺序约束。

| 请求 | 主机行为 |
| --- | --- |
| 不带 `imageKeys`（旧客户端） | 老分支：内联缩略图 + 240KB 预算 + 最近 12 条窗口 |
| 带 `imageKeys: true` 且该图**有内容 key** | 新分支：`key` + `thumb` + 尺寸 + `omitted`，**不占图片预算、不受窗口限制** |
| 带 `imageKeys: true` 但该图**无 key**（内联 base64） | 暂时回落老分支（见 §13 第二阶段：后台落库队列） |

**两边都可以独立发版**：主机先上不影响旧客户端；客户端先上（带标记）在旧主机上会被当未知字段忽略。

## 10. 安全

- key 是内容哈希，但**不是公开 URL**：`attachment.fetch` / `issueAttachmentUrl` 仍走
  `attachmentNameAllowed(threadId, name)` 的**会话作用域**校验（跨会话拿不到）。
- 直连 URL 是短时效令牌（`attachmentTokens.mint`），key 泄露 ≠ 可读。
- LQIP 只有几百字节，信息量极小。
- 新增的 `*.thumb.*` / `*.lqip.*` 放行必须**绑定父 key**，不能变成"任何名字都能取"。

## 12. 取舍与风险

| 场景 | 结果 |
| --- | --- |
| 主机在线 + 有缓存 | 与现在相同或更快（快照小得多） |
| 主机在线 + 无缓存 | 每次可见多一次往返（局域网几十 ms / 中继几百 ms） |
| **主机离线 + 未缓存** | 拉不到 → 只有 LQIP 或灰块。这是换取「快照不被图撑爆」的代价，UI 必须明说 |
| 主机重启后首次拉缩略图 | 依赖 §7-3 的父 key 判定，做错就是 404 风暴（必须单测覆盖） |
| `text` 档体积 500 KB | 单张下载变慢（有进度）；不做预取原图即无感 |
| 不做云端 | 主机离线时没有第二副本；要就得让中继存**密文分片**（协议改造 + 双真相源 + 隐私边界变化），本期不做 |
