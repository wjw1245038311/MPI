# MPI 交互规格（UI-SPEC.md）

> 面向：改 `src/renderer/**` 交互的人和 agent。
> 本文管**好不好用**（状态、防错、流程、反馈）；`docs/DESIGN-TOKENS.md` 管**好看**（值 + 违规判定）；
> `docs/DESIGN.md` 管设计取向。
>
> 为什么需要这份文件：AI 默认只交付 happy path。空态一片空白、loading 干转圈、错误弹一串技术串、
> 危险操作没有撤销 —— 这些截图看不出来，只有真用起来才暴露。所以它们必须**提前写进规格**，
> 而不是事后 review 时才发现。

---

## 0. 给 agent 的执行顺序（强制）

写任何交互组件前：

1. 在 §2 找到这个组件，**把状态矩阵每一行都实现**。表里没有的状态，先问，不要自己发挥。
2. 文案按 §4 的三要素写，不写「操作失败，请重试」。
3. 危险操作按 §3 处理，**只配确认弹窗算不合格**。
4. 交付时报告：实现了哪几个状态、每个状态截图或断言在哪、哪些状态你没做（并说明原因）。

## 1. 五态基线（所有数据视图的最低要求）

来自 About Face 4 第 15 章 + 社区收敛的 AI 交互缺陷清单。**任何展示数据的区域，五种状态都要有明确表现，缺一个就是不合格。**

| 状态 | AI 默认（不合格） | MPI 要求 |
|---|---|---|
| **default** | 假数据铺满 | 真实数据；长文本 / 极端值不能破版 |
| **loading** | 一个干转的圈 | 骨架屏（先给内容形状）+ **进度说明**（"正在拉取最近 30 天的消息…"） |
| **empty** | 空白，或灰字"暂无数据" | 说明这里是干嘛的 + **一个主操作入口** +（可选）示例 |
| **error** | `alert` 弹栈、或干脆没反应 | 三要素：发生了什么 / 为什么 / 怎么办，**措辞不责备用户** |
| **success** | 无反馈，或弹窗邀功 | 就地反馈（toast / 行内状态），不打断 |

### 1.1 三态细节要求

**空态**必须回答三个问题（Cooper：好店员不但指路，还告诉你更划算的选择）：

1. 这里是干嘛的（一句话）
2. 我现在能做什么（一个按钮）
3. 做出来大概什么样（示例 / 模板，可选但推荐）

✅ 好例子（MPI 已有）：`RemotePanel.tsx:479`
```
"还没有配对任何设备。用上面的二维码配一台。"
```
说了现状 + 指了下一步。**但缺一个动作按钮**（二维码在视觉上够近，可接受）。

❌ 反例：任何只写"暂无数据"的地方。

**loading** 三档（0.1s / 1s / 10s）：

| 等待时长 | 反馈 |
|---|---|
| < 0.1s | 不显示（闪烁更糟） |
| 0.1s–1s | 局部 spinner 或按钮 loading 态 |
| > 1s | 骨架屏 + 进度说明文字 |
| > 10s | 加进度百分比或「可能要一会儿」的预期说明 + 可取消 |

**error** 三要素公式：

```
发生了什么：<哪个操作没成功，本地数据还在不在>
为什么：    <人话原因，不写 HTTP 状态码 / 异常类名 / 文件名:行号>
怎么办：    <至少一条可点的出路>
```

措辞红线：**不责备用户**。"您输入了非法字符" → "这里只支持字母、数字和下划线"。

## 2. 状态矩阵（组件级，核心章节）

> 每加一个交互组件，在这里补一节。表格可以空着实现，但不能不填。

### 2.1 通用规范

| 状态 | 触发 | 展示 | 交互 | 依据 |
|---|---|---|---|---|
| default | — | 正常样式 | 可操作 | DESIGN-TOKENS |
| hover | 鼠标进入 | `--control-hover` / `--overlay-2` | — | strict.forbidden 无单态组件 |
| focus-visible | Tab 聚焦 | `--ring-accent`（3px） | 可键盘操作 | §6 键盘可达 |
| active | 按下 / 选中 | 强调（`--accent-soft` 或 650 字重） | — | — |
| disabled | 条件不满足 | 降透明度 | **必须有 tooltip 说明缺什么**，不能点了才报错 | About Face 4 |
| loading | 异步中 | 按钮内 spinner，**防重复提交** | 禁用点击 | §1.1 |

### 2.4 实例：应用商店（`components/AppStorePanel.tsx`）

> 选它的理由：2026-11-25 thinkbook16p 报「开关打开了但没生效」，查下来不是用户误操作，
> 而是**已启用的应用改完配置根本没有保存出口**——`saveConfig` 只在 `enable()` 里调，
> 而那个按钮只在未启用时渲染。表单能改、看着像生效、实际从未写盘。
> 这是 UI-SPEC §0 说的「只交付 happy path」的典型：只做了「首次启用」这一条顺路。
> 同一轮的第二个缺口：保存后服务不重新 activate，新值要等下次重启 MPI。

#### 配置表单与保存（`appstore-form` / `appstore-actions`）

| 状态 | 触发 | 实现 | 判定 | 备注 |
|---|---|---|---|---|
| default | — | 表单按 `config.fields` 渲染，值 = 保存值合并默认值 | ✅ | — |
| **dirty** | 表单值与已保存值不一致 | 动作行出现「有未保存的修改」（`--warn`），保存按钮从 disabled 转为可点 | ✅ **本轮补** | 以前无任何提示 |
| **saving** | 点了保存 | 按钮文案变「保存中…」并禁用；同轮禁用停用/重启/卸载，防重复提交 | ✅ **本轮补** | — |
| success | 保存完成 | toast：已启用时明确写「服务已重启——新设置立即生效」 | ✅ **本轮补** | 不弹模态，符合 §4.3 |
| **error** | 服务重启失败 | toast 三要素：设置已保存 / 服务没重启成功（带原因）/ 点「重启服务」再试 | ✅ **本轮补** | 关键：**说清值已存住**，别让用户以为白改 |
| disabled | 无改动 / 未启用 / 加载中 | 保存按钮置灰 | ✅ | tooltip 由 dirty 提示替代（同一行可见） |

#### 列表空态与加载态

| 状态 | 触发 | 实现 | 判定 |
|---|---|---|---|
| **loading** | 首次 `loadAppStore()` 未返回 | 两张骨架卡（图标块 + 标题块 + 两行文本块，1.4s 呼吸），`aria-busy` | ✅ **本轮补**（原来只有「加载中…」四个字） |
| **empty** | `entries.length === 0` | 标题说「还没有安装任何应用」+ 一段「应用能做什么」+ **主操作「从 zip 安装」** + 次操作「加载未打包目录」+ 一句「装完默认不启用，先看权限」 | ✅ **本轮补** |
| default | 有应用 | 卡片网格，enabled 卡片描边强调 | ✅ |

**空态为什么补了两段文字而不是一句话**：原实现是「还没有应用。点击右上角从 zip 安装」——
只指路，没回答「我为什么需要装」。§1.1 要求空态回答三问，其中第 3 问（做出来什么样）
靠「应用能把外部能力接进 MPI：接本地模型、跨设备收发消息、把语音换成本地模型」来答。

**为什么保存后自动重启而不是加提示**：配置值的消费方（pi 扩展 / 服务模块）读的是
`<userData>/apps/data/<id>/config.json`，只有 `activate` 会写它。加提示不给路径，用户
仍然不知道「改了没生效」该怎么处理；自动重启把这条正确路径做成默认。代价是保存会
重建服务（几秒内状态为 starting），对 devmail 这类无状态服务无感。

## 3. 防错与可逆（危险操作专用）

### 3.1 优先级：可逆 > 可确认

| 方案 | 何时用 | 代价 |
|---|---|---|
| **立即执行 + 撤销窗口**（首选） | 操作可回滚 | 需要后端支持 |
| **确认弹窗**（次选） | 操作不可回滚，但后果严重 | 打断流程，用户会养成"闭眼点确认" |
| **仅确认、无撤销**（不合格） | — | 本项目多处是这个状态 |

### 3.2 危险操作的视觉区分

危险按钮必须与常用按钮**拉开物理距离**，且不能只是同款按钮换个文字：

- 底色用 `--danger-strong` / hover `--danger-strong-hover`
- 文字用 `--send-fg`
- 至少间隔一个空位或分隔线

当前 `RemotePanel` 的"移除"用的是 `set-btn ghost` —— **与旁边的普通按钮完全同款**，违反本条。

### 3.3 disabled 必须解释

条件不满足时按钮置灰，**并在 tooltip 或同行说明里写清缺什么**。
不要"点了才报错" —— 那是把错误留给用户发现。

## 4. 文案规范

### 4.1 按钮：动词开头，说清后果

| ❌ | ✅ |
|---|---|
| 确定 | 保存 / 删除 / 移除设备 |
| 提交 | 发送 |
| 是 | 覆盖原文件 |
| 操作已完成 / 您的请求已被系统处理 | （不弹这种） |

动作名全程一致：按钮写"发布"，toast 就要写"已发布"。

### 4.2 错误文案三要素（§1.1 的落地版）

| ❌ AI 默认 | 为什么弱 | ✅ |
|---|---|---|
| 操作失败，请重试。 | 没说哪个操作；重试还是失败（病根没写） | 报销单没提交出去，草稿已保留。附件超过了 10MB。压缩一下或拆成两张单子。 |
| Error 422: Unprocessable Entity | 状态码是给开发者的日志 | 收货信息没保存上。手机号少了一位（现在 10 位）。补上就能提交。 |
| 您输入了非法字符！ | "非法"+"感叹号"= 责备用户 | 用户名只支持字母、数字、下划线。空格换成下划线就行。 |

### 4.3 不邀功

成功的操作**不弹模态**。用行内状态或 toast。
现有 `pushToast("success", ...)` 已符合。

## 5. 验收（怎么证明做到了）

### 5.1 交互必须「上手点」，不能只看截图

审美的病截图能看出来；交互的病必须**调慢网络、清空列表、按下危险按钮、走完全程**。

验收四个动作（每次改动都跑）：
1. **清空列表** → 空态是否教了下一步？
2. **调慢网络 / 断网** → loading 有进度说明吗？错误有三要素吗？
3. **按危险按钮** → 能撤销吗？和普通按钮分得开吗？
4. **只用键盘走完整流程** → Tab 顺序对吗？焦点环可见吗？Esc 能关浮层吗？

### 5.2 可自动化部分（Electron 侧）

### 5.3 14 项交互验收清单（可直接当打回话术）

**状态 3 项**
1. 加载、空、错误三态齐吗？（白屏和光秃秃「暂无数据」都算不齐）
2. 每次点击 0.1 秒内有反馈吗？超 1 秒的操作给进度了吗？
3. 把网络调慢点一遍，有没有假死？双击会不会重复提交？

**防错与可逆 3 项**
4. 危险操作可撤销吗？（只配了确认弹窗算不合格）
5. 条件不满足的按钮置灰并说明缺什么了吗？还是点了才报错？
6. 「删除」「清空」和常用按钮拉开距离了吗？

**流程 2 项**
7. 这个流程能砍掉一步吗？
8. 有没有让用户重填它已经知道的信息？

**习惯用法与控件 3 项**
9. 有没有发明非标准交互？
10. 互斥用单选钮、多选用复选框、立即生效用开关吗？
11. 选项超过一屏用下拉吗？

**文案 2 项**
12. 按钮说清后果了吗（"删除"而非"确定"）？
13. 标签用用户的话，不是系统的内部叫法吗？

**体贴 1 项**
14. 它记住用户上次的选择了吗？

### 5.4 打回话术对照（同一件事，改对概率差十倍）

| | 打回理由 | 效果 |
|---|---|---|
| ❌ | 「交互不太好用，再优化一下」 | AI 会去改配色 |
| ❌ | 「用户体验有待提升，参考大厂产品」 | AI 会去加渐变和卡片 |
| ❌ | 「整体重做一版，这次注意细节」 | 更差，随机性更大 |
| ✅ | 「删除没有撤销，只有确认弹窗。改成：立即执行 + 5 秒撤销 toast + 回收站保留 30 天」 | 可执行 |

**规则：打回理由里必须包含「哪个组件 / 哪个状态 / 改成什么」。**

### 5.5 EARS 格式写验收标准

EARS = Easy Approach to Requirements Syntax（Mavin 等，Rolls-Royce，2009；Airbus / NASA 在用）。
四种句式，**关键词决定测试类型**：

| 关键词 | 用法 | 对应测试 |
|---|---|---|
| **When** | 事件触发行为 | 事件驱动测试 |
| **While** | 状态相关行为 | 状态条件测试 |
| **If-then** | 条件行为 | 分支覆盖测试 |
| （无） | 恒定行为 | 基础功能测试 |

同一需求两种写法：

❌ 「移除设备要有确认」
✅
```
When 用户点击「移除」，系统立即执行并在 5 秒内显示可撤销 toast；
While toast 可见，点击撤销恢复该设备令牌；
If 5 秒内未撤销，令牌永久失效，该手机需重新扫码配对。
```

第二种模型能自检。**新交互一律用 EARS 写。**
