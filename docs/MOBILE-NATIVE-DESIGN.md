## 1. 目标与设计原则

### 1.1 最高优先级：交互流畅 + 软件稳定

本项目的最高目标是**交互流畅友好、软件稳定**。这不是口号，而是所有取舍的**最终仲裁者**：任何设计、技术或功能决策与这两条冲突，一律让路。

优先级排序（自上而下，冲突时上位胜出）：

1. **稳定** —— 不崩、不丢消息、不静默失败、断线能自愈
2. **流畅** —— 键盘跟手、滚动不掉帧、点击有即时反馈
3. **友好** —— 状态可见、错误可懂可操作、空态有引导
4. **功能** —— 在以上都达标的前提下再加
5. **好看** —— 动效与视觉修饰属锦上添花

**「友好」的具体含义**（可验收，不是感觉描述）：

| 场景 | 要求 |
| --- | --- |
| 任何失败 | 明确文案 + **一个可操作按钮**（重试 / 切换设备 / 看诊断），禁止只有「出错了」 |
| 重要错误 | 不用一闪而过的 toast 承载（toast 只用于「已复制」这类无后果反馈） |
| 连接状态 | 常驻可见（顶部状态点），用户随时知道「我现在连没连上」 |
| 发送消息 | 乐观插入列表；失败后保留在原位并带重试，**绝不静默消失** |
| 空态 | 三种空态（未配对 / 无会话 / 设备离线）各有引导，不留白屏 |
| 等待 | 超过 1s 的操作必须有 loading 或进度，禁止「点了没反应」 |

### 1.2 减法清单（稳定与流畅的另一面）

功能越多，不稳定面越大。v1 **明确不做**：

| 不做 | 原因 |
| --- | --- |
| 通知栏「就地批准」（留 v2） | 要求后台进程持有密钥并跑协议，复杂度与安全面俱增（见 §8.1） |
| iOS | 本工程是 Android 原生栈；另做一套 iOS 等于重写全部 UI 与网络层，自用无此需求（见 §2.2 的跨平台讨论） |
| Plan 结构化审核卡 | PWA 也没做，属 v2 |
| 手机端改文件 / 完整编辑器 | 协议有 `file.preview`，但体验与稳定性成本高，非核心 |
| 首页 15 个功能胶囊（抄千问） | 千问自己在被批评后要做减法（见 §7 #4） |
| 炫技动效 / 复杂手势 | 与「流畅」目标直接冲突 |
| 依赖注入框架（Hilt 等） | 单人项目不需要，手写简单容器即可；少一层框架 = 少一处维护面 |

**默认不做的还有**：任何「顺手加一下」的小功能——先回答它是否威胁稳定与流畅。

### 1.3 为什么做原生版：四个硬伤

现有 WebView 壳（APK 0.2.9 / `com.mpi.remote`）的四个硬伤，决定了这不是「样式不好看」这么简单：

| # | 硬伤 | 根因 | 原生版能否解决 |
| --- | --- | --- | --- |
| 1 | **锁屏审批做不到** | WebView 无 `PushManager` / service worker 推送（已实测 `pushManager=false`、`Notification=undefined`） | ✅ 原生通知 + 通知栏动作按钮 |
| 2 | **观感不像 App** | 全屏网页布局、浏览器滚动/回弹/字体，无原生动效 | ✅ Compose 原生渲染，无 WebView 参与 |
| 3 | **后台不可靠** | WebView 随 App 挂起即断 WSS | ✅ 前台服务常驻长连接 |
| 4 | **页面版本靠 hack** | `__mpi_build` 对比 index.html → `reload()`（见 `ANDROID-SHELL.md` #11） | ✅ 版本随 APK 发布，不再有「看到旧页面」 |

### 1.4 不解决的问题

**不解决的问题**（诚实标注）：原生版**不**带来新的模型能力、不改变中继可达性、不解决「桌面关机就什么都没了」。它是一次**客户端体验重做**，不是架构升级。

### 1.5 稳定与流畅的工程约束

把 §1.1 的原则转成可验证的硬指标。**每阶段验收都包含本节**——功能做出来但卡顿或丢消息，视为未完成。

**性能与稳定性预算**：

| # | 指标 | 目标 | 手段 |
| --- | --- | --- | --- |
| 1 | 冷启动到可交互 | < 1.5s | 延迟建连；首屏不阻塞在 WSS 握手上 |
| 2 | 点击到视觉反馈 | < 100ms | 乐观渲染，不等服务端回执 |
| 3 | 流式 token 刷新 | 批量节流（约每 60ms 一帧），**禁止每个 token 一次状态更新** | 累积 buffer + 定时 flush 到 `StateFlow` |
| 4 | 长会话（2000+ 条）滚动 | 60fps 不掉帧 | `LazyColumn` 虚拟化 + 工具卡折叠时**不参与组合** |
| 5 | 内存 | 不随会话长度线性增长 | 虚拟化 + 折叠态不保留展开内容 + markdown 渲染结果缓存 |
| 6 | 断线恢复 | < 5s 自动重连；重连后 `thread.resync` 不丢不重 | OkHttp WebSocket 自动重连 + seq 补齐 |

**已知稳定性风险与对策**（按严重度排序）：

| # | 风险 | 表现 | 对策 |
| --- | --- | --- | --- |
| 1 | 长会话渲染爆炸 | 会话变长后卡死、滚动掉帧 | `LazyColumn` + 稳定 `key`；工具卡折叠态**不进组合**；单条消息只重组自身 |
| 2 | 流式 token 重组风暴 | 输出时整屏抖动、输入框卡顿 | 见预算 #3；只把最后一条消息标记为「正在更新」 |
| 3 | 断线 / resync 失败 | 消息停在半截，用户不知道 | 顶部状态点常驻；重连失败给「重试」；resync 后校验 seq |
| 4 | 发送静默失败 | 消息发出去没反应，用户以为已发 | 乐观插入 + 失败态 + 重试按钮（见 §1.1） |
| 5 | 键盘 / 输入法不跟手 | 荣耀 MagicOS 上尤其明显 | `WindowCompat.setDecorFitsSystemWindows(false)` + `imePadding()` + `adjustResize`，**M2 真机验证，不接受模拟器结论** |
| 6 | 前台服务被系统杀 | 审批通知漏收 | 引导加白名单 / 关省电优化；启动时检测存活状态（见 §8） |
| 7 | 多设备切换竞态 | 切到 B 后收到 A 的旧帧 | 切换时先关闭旧 WebSocket；连接打 generation id，丢弃过期帧 |
| 8 | E2E 解密失败 | 白屏或内容错乱 | 明确错误文案 + 引导重新配对，绝不白屏 |
| 9 | 中继不可达 | 打开就卡住 | 首屏不阻塞；离线态可见 + 自动重连；本地草稿不受影响 |
| 10 | **加密实现与 PWA 不一致** | 配对成功但消息解不开 | **JUnit 跑同一套向量**（见 §2.4），本地即可证伪，不上真机试错 |

## 2. 技术路线：Kotlin + Jetpack Compose

### 2.1 决策过程（留痕，避免反复）

选型经历了两轮，结论翻转了一次，**过程值得记录**：

| 轮次 | 权重 | 结论 |
| --- | --- | --- |
| 第一轮 | 复用度（能省多少代码） | 推荐 React Native——PWA 有约 2265 行协议/加密/会话逻辑可复用 |
| **第二轮**（用户提出「长期维护成本」） | 维护成本 + 体验上限 | **改为 Kotlin + Compose** |

**翻转的关键**：RN 的维护代价不是抽象的——它有明确机制（见 §2.2），且「冻结版本就不用维护」这个想法被证据否掉了（冻结只会把成本推后并放大）。

### 2.2 为什么否决 React Native：维护成本调研

**结论：RN 的长期维护成本确实更高，用户的判断成立。**

| 证据 | 内容 |
| --- | --- |
| 官方社区调查（State of RN） | 「版本升级」被列为开发者**首要痛点之一**；同时上榜「难调试」「包无人维护」「过度依赖第三方库」 |
| 升级工程量 | 跨几个版本的升级（如 0.71→0.74）含原生模块，**需 2–4 周** |
| **冻结策略的真实代价** | 案例：某 App 自 2019 年停留在 RN 0.61 未升级，到 2023 年**大部分 npm 库已废弃，最终只能整体重写** |
| 框架换血中 | Bridge → 新架构（Fabric / TurboModules / JSI），v0.76+ 默认新架构；迁移期存在 ABI 不兼容、混合架构下内存泄漏与线程安全问题 |

⚠️ 上述数字多来自厂商/外包公司博客，**属方向性参考，非权威数据**。Flutter 与 RN 的「维护成本对比」各来源互相矛盾（有称 Flutter 低 50%，也有称取决于团队），**单一来源的百分比不可信**。

**剥离不适用的部分**（避免过度恐慌）：

| 成本项 | 是否适用本项目 | 原因 |
| --- | --- | --- |
| 商店合规（每年追 targetSdk） | ❌ | 个人自用、不上架，无 Play 强制 |
| 监控 / 回归测试团队开销 | ❌ | 单人使用 |
| 外包维护费（€2500–6000/月） | ❌ | 自维护 |
| **构建环境腐化** | ✅ **适用** | RN 需同时锁 **Node + JDK + Gradle + AGP + RN** 五方版本，任一方变动都可能构建失败 |
| **依赖生态腐化** | ✅ **适用** | npm 侧包维护参差；AndroidX 侧生命周期长得多 |
| **Android 平台行为变更** | ✅ 适用，**三者共担** | 前台服务类型强制声明（A14+）、通知权限（A13+）、后台限制——RN / Flutter / Kotlin 都要面对，因为最终都要写 Kotlin |

**决定性的一条**：我们已决定 **iOS 不做**（§1.2）。跨平台框架的核心价值就是「一套代码两端用」，这个价值在本项目**归零**，却仍要为此承担框架层与它的生态。

### 2.3 Kotlin 路线的风险与对冲

选了 Kotlin 就必须正视它的代价：**零逻辑复用，协议层全部重写**。三条对冲手段，把风险压到可接受：

| 风险 | 对冲手段 | 何时验证 |
| --- | --- | --- |
| **加密 / 配对与 PWA 不一致** | 把 `scripts/test-e2e-crypto.mjs` 里的 **RFC 官方向量**移植成 Kotlin JUnit 测试；`mobile/shared/protocol.ts` 作为类型契约；TS 实现作为**参考实现**逐行对照 | **M0，本地** |
| AI 写 Kotlin 出错 | 本地 `gradle assembleDebug` 编译验证（JDK21 / android-sdk / Gradle 8.10.2 环境已在壳项目跑通），**编译不过不交付** | 每次交付前 |
| 用户无法有效验证 | Kotlin 语法与用户 C#/C++ 背景接近（类、属性、空安全、扩展函数），**用户能读懂代码**——这比省几小时写码更重要 | 持续 |

**继承的验证资产**（这是 Kotlin 路线仍然可控的核心原因）：

| 资产 | 用途 |
| --- | --- |
| `mobile/shared/protocol.ts` | 协议类型契约（消息结构、方法名） |
| `scripts/test-e2e-crypto.mjs`（RFC 8291 / 7748 官方向量） | 移植为 Kotlin 单测 → 证明字节级一致 |
| `scripts/test-pwa-pairing.mjs` | 配对挑战-签名流程的**行为规格** |
| `mobile/pwa/src/lib/*.ts` | 参考实现（不复制代码，对照行为） |
| `ANDROID-SHELL.md`「手机端文件附件」 | 文件附件链路的已验证结论，直接照搬 |

**代价（如实记录）**：

| 项 | 估算 | 说明 |
| --- | --- | --- |
| 代码量 | 5000–6000 行 Kotlin（**未验证估算**） | 含协议层 + Compose UI |
| 首次打磨轮次 | 比复用路线多若干轮真机验证 | 一次性成本 |
| 与 PWA 的关系 | 两套独立实现，不再共享代码 | 改为共享「协议契约 + 测试向量」（见 §10） |

### 2.4 技术栈与工程结构

```
mobile/
├── shared/            ← 已有：protocol.ts（类型契约，三端共享，只读不改）
├── relay/             ← 不动
├── pwa/               ← 保留：浏览器 + 兜底，继续维护
└── app/               ← 新增：Kotlin + Compose 工程（包名 com.mpi.app）
    ├── app/src/main/java/com/mpi/app/
    │   ├── protocol/      ← 协议层：envelope、E2E、配对、seq resync（对照 TS 重写）
    │   ├── data/          ← OkHttp WebSocket、仓库层、DataStore/Keystore 存储
    │   ├── ui/            ← Compose 界面
    │   │   ├── home/      ← 首屏（欢迎 + 输入条 + 最近会话）
    │   │   ├── thread/    ← 对话页（消息流、审批卡、chip 行）
    │   │   ├── drawer/    ← 一级抽屉（项目/会话）+ 二级（设备）
    │   │   ├── settings/  ← 设置、诊断
    │   │   └── theme/     ← 设计令牌（§5）
    │   └── native/        ← 前台服务、通知、录音（AudioRecord）、相机（CameraX + ML Kit）
    └── app/src/test/      ← JUnit：协议层与加密向量测试（不进真机）
```

⚠️ **目录命名警告**：仓库根目录的 `android/` 是**旧 WebView 壳（冻结）**；新原生工程在 `mobile/app/`。两者不是一回事，别改错。

**技术选型**（都选长期维护有保障的官方/主流库）：

| 关注点 | 选择 | 理由 |
| --- | --- | --- |
| UI | Jetpack Compose + Material3（自定义 colorScheme） | 官方栈，长期维护 |
| 网络 | **OkHttp WebSocket** | Android 事实标准，Square 长期维护 |
| JSON | kotlinx.serialization | 官方，无反射坑 |
| 加密 | **BouncyCastle**（Ed25519 / X25519）+ JCE（AES-GCM）；HKDF-SHA256 手写（约 30 行） | Android 对 Ed25519/X25519 的原生支持随版本而异，BC 可控且一致 |
| 存储 | DataStore + Android Keystore（敏感字段） | 官方 |
| 状态 | ViewModel + StateFlow | 官方 |
| 依赖注入 | **不用框架** | 见 §1.2 减法清单 |
| Markdown | 自写轻量渲染（对照 `markdown-lite.ts` 的行为） | 避免引入重型库 |

**加密实现的注意点**（写代码时逐条核对）：

- SPKI PEM 的生成必须与 PWA 的 `device-identity.ts` **逐字节一致**（含固定的 `ED25519_SPKI_PREFIX`）——`deviceId` 由 PEM 哈希得出。
- `base64url` 用 `java.util.Base64.getUrlEncoder().withoutPadding()`，与 PWA 的 `toBase64Url` 对齐。
- HKDF 的 `info` 串、空 salt、输出 32 字节，全部照 `e2e-crypto.ts`。
- AES-GCM 输出布局 `ciphertext ‖ tag`（JCE 默认即此布局，与 WebCrypto 相同）。

### 2.5 M0 证伪清单（**先跑这个，再谈其它**）

以下每条若不成立，路线要当场改。**不要等 M4 才发现。**

| # | 待验证假设 | 状态 | 验证方式 | 环境 | 不成立时的退路 |
| --- | --- | --- | --- | --- | --- |
| 1 | BouncyCastle 的 X25519 / Ed25519 输出与 Node / PWA **字节一致** | ✅ **已验** | 移植 RFC 向量跑 JUnit，含双向互验 | 本地 | 换 Tink，或按 RFC 7748 手写实现 |
| 2 | OkHttp WebSocket 能连 relay 的 `wss://` 并承载 E2E 帧 | ✅ **已验** | 本地拉起真 relay，走完 hello 握手 | 本地 | — |
| 3 | `LazyColumn` 在 2000 条消息下滚动达 60fps | ✅ **已验** | 见下方实测数据 | 模拟器（真机待 M3 复核） | 分页加载历史 + 更激进折叠 |
| 4 | Compose 键盘避让在荣耀真机跟手 | ⏳ 待验 | M2 真机实测 | **真机** | 回退 `adjustResize` 手动偏移方案 |
| 5 | 前台服务在 MagicOS 可存活（含 A14+ 的 `foregroundServiceType` 声明） | ⏳ 待验 | 真机挂 2 小时看通知是否漏 | **真机** | 降级为「打开 App 才收」（等同壳），或转厂商推送（§8） |
| 6 | gradle / AGP / 依赖在国内可下 | ✅ **已验** | 直接构建通过（未加任何额外镜像） | 本地 | 手动预置依赖 |

#### 证伪项 3 的实测数据（2026-09，雷电模拟器 LDPlayer 14 / Android 14 / x86_64）

2000 条消息（混入助手段落 / 用户气泡 / 折叠工具行三种真实行形态），连续快速滑动 14 次：

| 指标 | 结果 | 预算（§1.5 #4） |
| --- | --- | --- |
| 渲染帧数 | 1391 | — |
| 卡顿帧 | 1（0.07%） | — |
| 50th / 90th 百分位 | 5ms / 6ms | < 16.7ms（60fps） |
| 95th / 99th 百分位 | 9ms / 12ms | — |
| 丢帧 / 慢 UI 线程 | 0 / 1 | — |

**结论：`LazyColumn` 虚拟化在 2000 条量级有充足余量，不需要分页。**

⚠️ 两点如实说明：

- **这是模拟器数据**（虚拟化 GPU、x86_64），绝对值不能直接外推到真机；能成立的是**相对结论**——虚拟化没有病态开销，余量很大。真机复核放在 M3（届时有 Markdown/diff/图片等真实渲染）。
- 统计里的 `Number High input latency: 843` **不是应用问题**：`adb shell input swipe` 是注入事件，与本机 `Vsync` 天然不同拍。此项在模拟器 + 注入场景下不可作数，真机手滑时另看。

### 2.6 版本冻结与升级策略

**教训**：RN 那条「冻结 → 最终重写」的案例说明——**没有升级策略的项目，维护成本会以复利方式累积**。Kotlin 栈虽然更稳定，同样需要策略。

| 项 | 策略 |
| --- | --- |
| 默认姿态 | **不追新版本**。能用就不动，避免为升级而升级 |
| 升级触发条件 | ① 出现必须修的问题（安全 / 兼容 / 崩溃）② 目标 Android 版本的行为变更导致功能失效（如前台服务类型、通知权限） |
| 升级节奏 | 每次只升一个层次（先 Gradle/AGP，再 Kotlin，再 Compose），**不跳大版本合并升级** |
| 升级前必做 | 跑全部 JUnit + 真机走一遍 §11 的验收脚本；确认可回滚（打 tag / 留 APK） |
| 版本记录 | 在工程内维护一份 `mobile/app/VERSIONS.md`：记录 Gradle / AGP / Kotlin / Compose BOM 的当前版本与升级历史 |
| 依赖来源 | 只引入「官方或长期维护」的库（见 §2.4 表），**不引入小众/停更库** |

## 7. 千问避坑清单（实证，比它的优点更值钱）

千问的用户负面反馈**几乎全部集中在交互细节，而非模型能力**。以下坑 MPI 直接避开：

| # | 千问的坑 | 原文/依据 | MPI 的做法 |
| --- | --- | --- | --- |
| 1 | **键盘弹出不跟手** | 「输入键盘弹出不丝滑这个问题只在千问上出现，豆包、Kimi、元宝、DeepSeek 都没有」 | Compose 用 `imePadding()` + `adjustResize`，**M2 就上真机验证**，不拖到后期 |
| 2 | **右上角不是「新对话」** | 「新对话需要从侧边栏操作，导致很多用户不小心让上下文污染了后续对话」 | 右上角 `＋` **就是**新建会话 |
| 3 | 历史记录页缺操作 | 「历史记录页面里复制和分享按钮消失」 | 会话项长按 = 重命名 / 置顶 / 删除 |
| 4 | 首页功能密度过高 | PM 诊断列为「必做的减法题」：「把用户最高频的三到五个场景放到最显眼位置」 | 胶囊只放 **3–4 个**，不抄那 15 个 |
| 5 | 新用户不知道说什么 | 「面对一个充满功能入口的首页和一个不知道该说什么的对话框」 | 首屏 3 条示例必须**指向 MPI 真实能力**（看进度 / 新建会话 / 切设备） |
| 6 | 冷启动缺引导 | 同上，被列为「优先级一」 | 首次进入给一次性的轻引导（可跳过，不重复出现） |

> 参考文档稀缺性说明：千问是闭源商业产品，**阿里从未发布千问的设计规范 / 设计系统 / 组件库文档**。上述结论来自第三方产品拆解（见 §附录）与公开口碑，**非官方设计文档**，请按「二手证据」对待。阿里系可参考的官方规范是 Ant Design Mobile 与 mPaaS/AntUI，但**没有证据表明千问使用了它们**。

## 8. 推送与保活

大陆环境 + 荣耀 MagicOS，方案按可靠性排序：

| 方案 | 可靠性 | 代价 | 结论 |
| --- | --- | --- | --- |
| **A. 前台服务 + WSS 常驻 + 本地通知** | 高（进程活着就收得到） | 常驻通知栏一条、耗电；需引导用户加白名单 / 关省电优化 | ✅ **v1 采用** |
| B. 荣耀 / 华为 HMS Push | 中（依赖厂商服务） | 需厂商开发者账号与证书；非华为系机型不通 | 备选 |
| C. 飞书机器人 / Server酱 | 中（需装飞书） | 与 App 割裂，点开只能跳浏览器 | 备选 |

**v1 = 方案 A**：relay 本来就是长连接，App 侧用 `ForegroundService` 维持 OkHttp WebSocket，收到 `ui.request` / 任务完成即发本地通知。

**实现注意**：

- Android 14+ 必须声明 `foregroundServiceType`（本场景用 `dataSync` 或 `specialUse` 并说明用途），否则启动即崩。
- Android 13+ 通知权限需运行时申请（`POST_NOTIFICATIONS`）。
- 前台服务的常驻通知要做得**不烦人**（简洁文案 + 可关闭入口，但关闭即失去审批推送——需明确告知代价）。

### 8.1 关键设计约束：通知栏「直接批准」是 v2

| 版本 | 能力 | 原因 |
| --- | --- | --- |
| **v1** | 通知 → 点击打开 App → **直达审批卡** | 路径短、风险低，体验已接近千问 |
| v2 | 通知栏 action 按钮**就地批准** | 要求后台服务能完成 E2E 解密 + 发 `ui.respond`，即让协议层在无 UI 的情况下跑通。本工程是 Kotlin，**技术上比 RN 更可行**（无 JS 运行时限制），但仍涉及密钥在后台进程的使用面，留待 v2 单独评估 |

> v1 明确不做就地批准。宁可少一个功能，先不让后台进程承担解密职责。

| --- | --- | --- |
| **PWA**（`mobile/pwa`） | 浏览器直用 + 免安装兜底 + **协议参考实现** | 继续维护 |
| **WebView 壳**（`android/`） | 不装原生 App 时的兜底 | 保留，**冻结维护**（只修 bug，不加功能） |
| **原生 App**（`mobile/app`） | 主力体验 | 新增 |

**三者的共享物**（语言不同，共享的是契约而非代码）：

```
mobile/shared/protocol.ts    ← 协议类型契约（三端共同遵守）
测试向量（RFC 8291 / 7748）  ← 加密实现一致性的唯一裁判
docs/（本文件 + MOBILE-DESIGN.md）
```

**代价（诚实说）**：协议层会有**两份独立实现**（TS 一份、Kotlin 一份）。它们之间靠「类型契约 + 加密测试向量 + 配对行为规格」保证一致，而不是靠共享代码。这意味着：**改协议时必须同步改两处**，且每次都要跑两侧的测试。个人自用可接受，但这是长期成本。

## 11. 分阶段实施

| 阶段 | 内容 | 验收标准 |
| --- | --- | --- |
| **M0** 骨架与证伪 | Kotlin/Compose 工程 + gradle 镜像 + 协议层（配对 + E2E）+ JUnit 向量测试 | ① §2.5 的**本地可验证项（1/2/3/6）**全部有结论 ② 加密向量 JUnit 通过（**字节级一致**）③ 编译通过 |
| **M1** 打通协议 | OkHttp WebSocket 接 relay + 会话列表 + 存储（Keystore/DataStore） | 真机配对成功，看到项目与会话列表 |
| **M2** 对话主流程 | 消息流 + 发送 / steer / abort + 审批 Sheet + chip + **键盘跟手验证** | 真机完成一轮「看进度 + 发指令 + 批准」；键盘无卡顿（§2.5 项 4） |
| **M3** 千问式外壳 | 顶部导航 + 抽屉 + 主题 / 设置 + 气泡与工具折叠 | 与千问并排比对布局与手感；明暗双主题无对比度问题 |
| **M4** 原生能力 | 录音、相机、文件、分享、扫码 | 语音输入在荣耀真机可用（不再有 WebView 的 `NotReadableError` 坑） |
| **M5** 常驻与通知 | `ForegroundService` + 本地通知 + 深链 | 锁屏收到审批通知，点开直达审批卡（§2.5 项 5） |
| **M6** 打包分发 | 扩展 `publish-android.mjs`、Seafile、自更新 | 与 `com.mpi.remote` 并存安装无冲突（§2.5 项 7）；Seafile 可下载 |

> **每阶段验收都包含 §1.5 的性能预算与稳定性门槛**。功能可用但卡顿、丢消息、静默失败，一律视为该阶段未完成——这条优先于本文其它任何功能描述。

**节奏建议**：M0–M2 是**价值验证点**。M0 结束时应已确认「加密是对的、能连上中继」；M2 结束后做一次真机对比，若体验不及预期，损失只有两个阶段。

**关于用户验证负担**：Kotlin 路线的真机验证轮次会多于复用路线，这是选型时已知并接受的代价（§2.3）。为降低负担，每个阶段的验收脚本应**尽量短且明确**（一次装包、走 3–5 个动作、看明确结果）。

## 12. 测试策略

| 层级 | 内容 | 环境 |
| --- | --- | --- |
| **加密 / 协议向量** | 移植 `scripts/test-e2e-crypto.mjs` 的 RFC 8291 / 7748 官方向量；配对挑战-签名流程 | **JUnit，本地**（关键：不上真机试错） |

| **真机手工** | 键盘跟手、抽屉手势、录音、通知深链、前台服务存活（2 小时挂机）、并存安装 | **真机（用户执行）** |
| 回归 | 动了协议层 → 同时跑 PWA 侧 `npm test` 与 Kotlin 侧 JUnit | 每次协议变更 |

## 13. 风险与止损

| 风险 | 应对 |
| --- | --- |
| §2.5 证伪项不成立 | **M0 当场改路线**，不硬撑 |
| 加密实现与 PWA 不一致 | JUnit 向量测试**本地**证伪（§12）；这是本路线最大的技术风险，也是唯一必须零容忍的一项 |
| 键盘 / 输入法兼容（荣耀 MagicOS） | M2 真机验证，不用模拟器糊弄 |
| 前台服务被 MagicOS 杀 | 引导加白名单；若仍不可靠，降级为「打开才收」或转厂商推送（§8） |
| 首次工作量与验证轮次偏多 | 已知代价（§2.3）；每阶段独立可验收；M2 后设「继续 / 放弃」决策点 |
| 协议层双份实现的漂移 | §12 的回归要求：改协议必须同改两侧并跑两侧测试 |
| 长期依赖腐化 | §2.6 版本冻结与升级策略 |
| 工作量失控 | 每阶段独立可验收；M2 后设一次「继续 / 放弃」决策点 |

**止损规则**：同一技术问题连续两次尝试无进展 → 停下上报，不硬撑（沿用协作约定）。
