# 「分享给朋友」：自建中继的服务化设计

> 目标读者：中继运营者（你）与将来要接入的朋友。
> 相关实现：`mobile/relay/index.mjs`（中继）、`src/main/remote/relay-uplink.ts`（主机上行）、
> `src/main/remote/e2e-crypto.ts`（E2E）、`docs/attachment-content-addressing.md`（附件内容寻址）。
>
> 一句话：**内容加密这一层已经够了**（中继读不到消息与附件），真正缺的是
> **① 准入（别被白用）② 局域网免中继 ③ 附件在朋友场景的分工**。

## 一、需求与信任模型

需求（用户原话整理）：

1. 朋友装客户端 + 只填「你给的中继地址」即可用；不装 Tailscale、不自己在公网暴露端口。
2. 朋友手机与电脑在**同一局域网**时，不经过你的中继。
3. **你作为中继运营者读不到朋友的内容** —— 内容必须端到端加密。

信任模型（把话说白，朋友需要知道）：

| 角色 | 能看到 | 看不到 |
|---|---|---|
| 你（中继运营者） | 哪些 hostId/deviceId 在线、何时、帧大小、推送文案（见 §四）、下载日志 | **消息、快照、附件字节、配对协商出的会话密钥** |
| 链路中间人 | 同样只有元数据（控制帧与附件都是应用层 AEAD 密文） | 同上 |
| 朋友自己的主机 | 自己会话的全部内容 | 别人的（按 hostId 分租户，互不可见） |

同时也明说三个**加密解决不了**的边界：你能拒服务/下线任何主机；你掌握软件分发（可下发不同版本）；朋友越多你的账单越高（§六）。

## 二、现状盘点（代码事实，2026-09-30）

| 能力 | 现状 | 差距 |
|---|---|---|
| 控制通道 E2E | 配对时 X25519 协商 → HKDF → AES-256-GCM；中继只转发密文（`e2e-crypto.ts`） | ✅ 无 |
| 附件应用层加密 | 客户端声明 `X-MPI-Enc: v1` → HKDF(会话密钥)+AES-GCM 逐片，AAD 绑位置 | ✅ 无 |
| 主机标识 | `hostId = hostIdFor(身份公钥)`（每套安装自生成，不可自定） | 中继据此分租户 ✓ |
| 中继准入 | **无**：`host.register` 不校验任何凭证；`hosts/devices/tickets` 全在内存 | ❌ 任何人可白用 |
| 中继配额 | 只有 `MAX_FRAME_BYTES=32MB`、`MAX_TICKETS=1000`；无 per-host 限流/统计 | ⚠️ 无成本感知 |
| 推送 | 主机发**明文** `push.request{kind,title,body,deepLink}`；中继用订阅密钥加密后投递；VAPID 私钥持久化在中继 | ⚠️ 中继能看到文案（当前只有固定文案 + `threadId`） |
| 局域网直连 | **不存在**：手机端只把「中继地址」当 URL；桌面端不自带中继服务 | ❌ 需求 2 未实现 |
| 附件公网入口 | 工作站靠**一条反向 SSH 隧道**挂到 ECS（`ssh -R …:8899`）；仅 IP + 明文 HTTP + 应用层加密（域名会被备案拦、TLS 会被握手指纹 DPI 掐） | ⚠️ 每台主机一条，**不可扩展** |

## 三、要补的三件事

### 3.1 中继准入（P1，小改动）

**做法**：主机 `host.register` 带 `hostToken`；中继侧维护允许列表。

- 中继：新增 `RELAY_HOST_TOKENS`（逗号分隔）或 `RELAY_TOKEN_FILE`（每行一个，便于热改）；
  校验失败 → `relay.error{code:"HOST_UNAUTHORIZED"}` 并断开。
- 桌面端：新增配置 `remoteRelayToken`（与 `remoteRelayUrl` 同级），上行注册时带上。
- **token 只用于 host→relay 注册，绝不放进配对票**（否则朋友的手机也拿到主机凭证）。配对票里继续只带 `hostId`、中继地址、`hostX25519Pub`。
- 吊销：改 token 文件 + 重连（或中继支持 SIGHUP 重读）。可选：支持「一朋友一 token」便于精确吊销与统计。

**代价**：中继 ~20 行 + 桌面端一个配置字段 + 一处文档。**收益**：止住白用，也给后续配额/统计留了抓手。

### 3.2 局域网直连（P2，已实现 2026-09-30）

**已落地做法 A**（见下表的理由）：桌面端自己拉一个**只绑局域网**的中继子进程。

- 开关：设置 → 远程 → 「局域网模式」（配置项 `lanModeEnabled` / `lanModePort`，默认 9001）
- 拉起方式：`spawn(process.execPath, [<relay>/index.mjs], { env: { ELECTRON_RUN_AS_NODE: "1", RELAY_HOST: "0.0.0.0", RELAY_PORT, RELAY_PLAIN_PORT: "", RELAY_HOST_TOKENS: "" } })`
  —— **与 ECS 上跑的是同一份 relay 文件**（不抄代码、不会漂移）；已实测 `ELECTRON_RUN_AS_NODE=1 electron index.mjs` 能正常起中继（打包版没有独立 node）。
- 脚本位置：开发取仓库 `mobile/relay/index.mjs`；打包由 `build.extraResources` 复制到 `<resources>/relay/index.mjs`（连同 `node_modules/ws`）。
- 地址：自动挑一张**手机能连到的**网卡（跳过 VMware/WSL/Tailscale/回环/169.254，私网优先 192.168 > 10 > 172.16-31），然后把
  · 配对票里的中继地址 → `ws://<内网IP>:<端口>/ws`；
  · 附件直连基地址 → `http://<内网IP>:8899`（**LAN 模式优先于配置里的公网入口**）。
- 固有取舍：**没有推送通道**（Web Push 要经公网中继），手机在后台收不到「待批准」通知，需回前台同步。界面上就这么告诉用户。

| 方案 | 做法 | 优点 | 代价 |
|---|---|---|---|
| **A. 桌面端内嵌「只绑局域网」的 relay（已选）** | 见上 | 手机端**零改动**（它本来就把地址当 URL 用）；复用全部现有协议与加密；附件同时切内网 | 需要能拿到本机内网 IP；局域网内开放两个端口（relay + 附件） |
| B. 手机直连主机 HTTP | 另写一套直连握手/心跳/重连 | 少一跳 | 与现有 `RelayClient` 抽象分叉、收益小 |

> 顺带解决一个隐性问题：LAN 模式下附件走内网 HTTP（明文但应用层加密），**不再需要反向隧道、也不再消耗你的 ECS**。

### 3.3 附件在朋友场景的分工（P1 文档 + 可选工程）

| 场景 | 附件怎么走 | 谁承担 |
|---|---|---|
| 同局域网 | **内网直连**（LAN 模式附带） | 朋友自己 |
| 不同网络、能接受慢 | 中继分片回落（`attachment.fetch`，约 1MB/s） | 你的 ECS（很小：分片经控制帧，但大文件仍走你的带宽） |
| 不同网络、要快 | 朋友**自己**解决公网入口（自己的 VPS / 内网穿透），把 `attachmentBaseUrl` 指过去 | 朋友自己 |
| ❌ 不要做 | 每台主机都挂一条反向隧道到你的 ECS | 端口/凭证/带宽都不可扩展 |

**可选工程项**：当附件回落中继且体积超过阈值（如 20MB）时，客户端提示「当前经中继中继，较慢；同网段更快」——把「为什么慢」说清楚，避免朋友以为软件有问题。

## 四、推送：把「不许塞内容」变成约束

- 现状：只有一处 `sendPush`，文案固定（「MPI 需要批准」+ `/thread/<id>`），**不含会话内容** ✓。
- 立规矩：`sendPush` 的 `title/body` **只允许固定文案**，`deepLink` 只放 `threadId`；新增单测钉住（禁止把回复摘要/文件名塞进去）。
- 可选（P3）：真 E2E 推送——把订阅私钥留在手机侧、由主机用其公钥加密载荷，中继只做密文投递。工程量中等（要改 Web Push 载荷生成位置），收益是「中继连通知文案也看不到」。当前文案无内容，优先级低。

## 五、运维手册

**朋友侧（三步）**：① 装包（桌面端 / 0.5.117+ 安卓）；② 设置里填中继地址（+ token，若启用准入）；③ 与自己的手机配对（扫自己那台电脑的二维码；票里带的地址决定走公网还是局域网）。
局域网用户：无特殊步骤——LAN 模式下配对票自带内网地址，什么都不用填（前提是桌面端开着 LAN 模式）。

**你这边**：

```bash
# 中继（ECS）关键 env
RELAY_PORT=9443                     # tailnet/TLS 监听（主机走这条，若在 tailnet 内）
RELAY_PLAIN_PORT=10445              # 公网明文监听（手机与不在 tailnet 的主机走这条）
RELAY_HOST_TOKENS=<token1,token2>   # P1 起：主机准入
RELAY_STATIC_DIR=/var/www/mpi-mobile/download   # APK / 更新清单
RELAY_TLS_CERT/RELAY_TLS_KEY        # 有证书时
```
- 发放/吊销：加/删 token → 重启中继（或重读文件）。建议一朋友一 token，便于单独吊销。
- 监控（P3 可选）：每 host 的连接数、帧数、字节数（现在中继全内存、无统计）。
- 下线某人：删其 token（P1 后有效）。

## 六、成本模型（朋友 N 人）

| 项 | 量级 | 说明 |
|---|---|---|
| 控制通道 | 心跳 + 加密帧，通常 < 10 KB/s/主机，空闲更低 | 中继主要成本是**连接数与内存**，不是带宽 |
| APK 分发 | 每次约 31MB | 谁装谁下，都走你的 ECS 公网（按量计费）；建议只给受信任的人直链 |
| 附件经中继回落 | 与文件体积同量级 | **唯一可能显著吃流量的项** → 所以 LAN 直连与「各自解决公网入口」是重点 |
| 内存 | 每主机一条 ws + 每设备记录 | 全内存、重启即清（host 会重连注册） |

## 七、分阶段落地

| 阶段 | 内容 | 现在的可用性 |
|---|---|---|
| **P0（不改代码）** | 小范围熟人先用：填中继地址即可；局域网场景让他们在局域网内自己跑一份 `node mobile/relay/index.mjs` 并填内网地址 | ✅ 今天就能 |
| **P1（已做）** | `hostToken` 准入 + 吊销（已含 5s 热重载）+ 配对票不含 token 的源码级守卫 + 本文档 | 已完成 |
| **P2（已做）** | 桌面端内嵌 LAN relay（一键开）+ 配对票写内网地址 + `attachmentBaseUrl` 自动切内网 | 设置里一个开关；手机用它给的地址配对即可 |
| **P3（可选）** | 每 host 用量统计/限速、E2E 推送、中继租户持久化、附件回落时的「慢」提示 | 按需 |

## 八、待拍板

1. **准入粒度**：一个全局 token（简单）还是「一朋友一 token」（可精确吊销、可统计）？
2. **LAN 模式默认值**：默认关（手动开）还是默认开？监听端口用默认 9001 还是可配？

## 九、中继可见面审计（2026-09-30）

结论先说：**内容层加密（AES-256-GCM）没问题，但握手没有把 E2E 公钥绑进签名，且手机端从不校验主机身份** ——
所以「经过中继的内容对中继保密」**目前只在「中继老实转发」的前提下成立**。要让它在「中继不可信」下也成立，
必须修下面这四条。

### 9.1 证据（代码位置）

| 事实 | 位置 |
|---|---|
| 双方签名的文本是 `mpi-remote-v1\|hostId\|connectionId\|challenge\|deviceId` —— **不含任何 X25519 公钥** | 主机 `src/main/remote/host.ts:292`；设备 `mobile/.../Pairing.kt:71`（`signedText`） |
| 主机的 X25519 公钥是在 `pair.accepted` 里**注入**的，而该帧属于 `PLAINTEXT_FRAME_TYPES`（明文） | `src/main/remote/relay-uplink.ts:68,381` |
| 设备的 X25519 公钥走 `pair.hello`（明文）且不在签名覆盖内 | `Pairing.kt:157`（`put("x25519Pub", …)`） |
| **安卓端读 `pair.challenge` 时把 `signature`/`hostPublicKeyPem` 丢掉了**（不验主机身份） | `Pairing.kt:141-148` |
| `deviceToken` 通过 `pair.approved` **明文控制帧**给中继（中继持有它） | `relay-uplink.ts:383` |
| 中继转发数据帧时是盲转（本身不看内容） | `mobile/relay/index.mjs`（data 帧 opaque） |

### 9.2 后果（威胁模型：中继不可信）

一个恶意（或被入侵的）中继可以：

1. **中间人换公钥**：把自己的 X25519 公钥分别发给两端（因为它能改写那两个明文帧），于是主机与设备各自
   与中继派生会话密钥，之后所有「加密」数据帧它都能解开 —— **内容对它就是明文**。
2. **冒充设备**：它持有明文 `deviceToken`，可以用自己的 X25519 公钥发起 `hello` 重新握手（若主机允许在
   `hello` 里轮换公钥），同样拿到会话密钥。
3. 推断元数据（无法避免）：谁在线、何时、帧大小、hostId/deviceId、推送文案。

### 9.3 修复方案（四步，建议优先于其它功能）

1. **把各自的 X25519 公钥绑进签名文本**：
   - 设备签：`mpi-remote-v2|hostId|connectionId|challenge|deviceId|<deviceX25519Pub>`
   - 主机签：`mpi-remote-v2|hostId|connectionId|challenge|<hostX25519Pub>`（主机公钥是身份派生的稳定值，
     `pair.challenge` 阶段就已知）
2. **手机端必须校验主机签名**（含 `hostPublicKeyPem` 与签名覆盖的 X25519 公钥），不通过就拒绝配对。
3. **主机在 `hello` 重新握手时不许轮换 X25519 公钥**：只认配对时那个（或要求新公钥也带主机签名）。
4. **`deviceToken` 不进明文控制帧**：改为 E2E 建立后由主机在**加密帧**里下发（首次配对时设备已经用
   `pair.hello` 证明了自己持有私钥）；或设备端只在 `hello` 里用它作凭证，主机不把它回传中继。

**兼容代价**：签名文本一变，旧客户端（0.5.117）与新主机就配不上 —— 需同时出新 APK 与桌面端，
并且**不要静默退回 v1**（应明确提示「请升级客户端，否则无法保证端到端加密」）。

### 9.4 推送载荷约束（已落成单测）

`push.request` 是明文控制帧，中继必然能看到 `title/body/deepLink`。已加源码级守卫
`scripts/test-push-privacy.mjs`：所有 `sendPush(...)` 调用点的 `title/body` 必须是**固定文案字面量**
（不得含插值），`deepLink` 只允许 `/thread/<id>`。新增推送若违反即测试失败。

## 十、风险

- **中继是你的单点**：你关掉/欠费，朋友的控制通道与推送就断（局域网模式不受影响）。
- **中继全内存**：重启后 host 需重连注册；不影响已配对的设备（自动重连）。
- **明文附件链路**：应用层加密保证内容，但**端口/地址可被扫描**（附件入口是 IP+端口的明文 HTTP）；不做服务发现、不响应未带令牌的请求（现有 `/att/xyz` → 403 ✓）。
- **推送文案**：一旦有人往里塞内容，中继就能看到——所以 §四的约束要落成测试，而不是约定。
